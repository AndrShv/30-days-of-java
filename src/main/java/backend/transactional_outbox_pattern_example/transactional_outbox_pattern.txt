1. ОБЩИЙ FLOW (ЖИЗНЕННЫЙ ЦИКЛ ПЛАТЕЖА И СОБЫТИЯ OUTBOX)
--------------------------------------------------------------------------------
[ Client / REST Consumer ]
        │
        │ 1. HTTP POST /api/v1/payouts (Payload: userId, amount)
        ▼
[ PayoutController ]
        │
        │ 2. Вызывает метод payoutService.createPayout(dto)
        ▼
[ PayoutService @Transactional ] ──────────┐
        │                                 │ (Единая ACID-Транзакция BDB)
        ├──► 3.1. Сохраняет PayoutEntity ──┤
        │         в таблицу "payouts"     │ • Оптимистично пишем обе записи
        │         (status = CREATED)      │ • В брокер (RabbitMQ) сети НЕТ!
        │                                 │ • При ошибке откатываются ОБЕ записи
        └──► 3.2. Сохраняет OutboxEvent   │
                  в таблицу "outbox_events"│
                  (status = PENDING) ─────┘
        │
        ▼ (Commit в PostgreSQL)
[ PostgreSQL Storage ]
  • payouts: [ id: uuid, status: CREATED, amount: ... ]
  • outbox_events: [ id: uuid, payload: JSON, status: PENDING ]
        │
        │ (Каждые N сек по расписанию)
        ▼
[ OutboxPublisherScheduler (@Scheduled) ]
        │
        ├──► 4.1. SELECT * FROM outbox_events
        │         WHERE status = 'PENDING' ORDER BY created_at LIMIT 50;
        │         (Использует индекс idx_outbox_status_created)
        │
        ├──► 4.2. Итерируется по списку событий и отправляет JSON payload
        │         в RabbitMQ через rabbitTemplate.convertAndSend(...)
        │
        └──► 4.3. При успехе: UPDATE outbox_events SET status = 'PROCESSED'
                  (При сбое: остается PENDING или FAILED для повторной попытки)
        │
        ▼
[ RabbitMQ / Exchange: payout_outbox_exchange ]
        │
        │ 5. Сообщение маршрутизируется в очередь payout_outbox_queue
        ▼
[ PayoutEventConsumer (@RabbitListener) ]
        │
        ├──► 6.1. Вычитывает JSON-строку из очереди
        ├──► 6.2. Десериализует в PayoutRequestedEvent через ObjectMapper
        └──► 6.3. Выполняет внешнюю логику (вызов эквайринга/банка/уведомлений)

2. В ЧЕМ ВООБЩЕ СМЫСЛ ПАТТЕРНА TRANSACTIONAL OUTBOX?
--------------------------------------------------------------------------------

❌ ПРОБЛЕМА "ПРОСТАЯ ОТПРАВКА В БРОКЕР":
Если выполнять запись в БД и отправку в RabbitMQ прямо в сервисе:

    @Transactional
    public void createPayout(...) {
        payoutRepository.save(payout); // 1. Пишем в БД
        rabbitTemplate.convertAndSend(...); // 2. Отправляем в RabbitMQ напрямую!
    }

Возникает критическая проблема Dual-Write (Двойной записи):
• База упала ПОСЛЕ отправки в RabbitMQ -> Событие ушло, но платежа в БД нет.
• RabbitMQ недоступен / сбой сети ПОСЛЕ сохранения в БД -> Платеж есть, но
  событие потеряно НАВСЕГДА (сервис-потребитель никогда о нем не узнает).

--------------------------------------------------------------------------------

✅ РЕШЕНИЕ ЧЕРЕЗ OUTBOX PATTERN:
Паттерн гарантирует концепцию **At-Least-Once Delivery** (доставка как минимум один раз)
и связывает запись данных с публикацией событий:

1. **Гарантия атомарности (ACID):**
   Бизнес-данные (`payouts`) и событие (`outbox_events`) записываются в БАЗУ ДАННЫХ
   в рамках ОДНОЙ локальной транзакции. Если БД падает — откатываются обе записи.

2. **Отвязка от сети брокера (Decoupling):**
   Основной бизнес-поток не зависит от того, доступен сейчас RabbitMQ/Kafka или нет.
   Даже если брокер упал на 2 часа, контроллер продолжит успешно принимать платежи
   и складывать события в `outbox_events`.

3. **Гарантированная доставка (Resilience):**
   Фоновый планировщик (`OutboxPublisherScheduler`) безопасно вычитает не отправленные
   события со статусом `PENDING` из базы и доставит их в брокер, как только сеть или
   брокер восстановят работоспособность.

3. СВЯЗКА OUTBOX PATTERN + IDEMPOTENT CONSUMER (ПОЛНАЯ КАРТИНА)
--------------------------------------------------------------------------------
Так как Outbox гарантирует доставку **At-Least-Once** (сообщение из-за сбоев сети
при UPDATE status в БД может отправиться 2 раза), на стороне **Consumer** ОБЯЗАТЕЛЬНО
должна стоять защита от дубликатов.

Именно для этого используется аспект из прошлого шага (`@IdempotentPayout` + Redis):

    [ Outbox Publisher ] ──(Отправка)──► [ RabbitMQ ]
                                            │
                                            ▼
                                  [ PaymentAspect (Redis) ]
                                            │
                                  ┌─────────┴─────────┐
                                  │ (Первый раз)      │ (Дубликат)
                                  ▼                   ▼
                           [ Consumer Executed ]  [ Skipped (Return null) ]
